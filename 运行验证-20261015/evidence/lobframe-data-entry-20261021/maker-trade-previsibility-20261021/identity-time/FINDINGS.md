# 50笔成交：被动侧工作标签与事前可见身份

结论：**该分钟存在真实的、早于成交报告的订单身份信息；被动侧43/50笔还有候选状态在两套时间字段上均严格更早。但这只是身份/时间证据，不能证明可提前拒绝成交、可预测不利选择或赚钱。** 全部50笔固定纳入，无新增数据，无模型/重放/交易，旧STOP不变。

## 1. 方向与逐侧覆盖：不把全窗口匹配充当前视信息

工作映射复用同单元side-source/FINDINGS.md：官方供应商mapper将type0映射为canonical buy，Data Types将side定义为taker/aggressor；本样本type0有46笔，type1有4笔。因此按供应商映射，46笔被动侧为sell_order_id/ask，4笔为buy_order_id/bid，无异常type。该解释不等于个人maker到账，也不证明2026后台逐版本同一；被动角色是观察成交后的标签，不是当时已知输入。

每列固定分母50；A/B/C等维度可以重叠，不强凑成互斥组：

| 检查维度 | buy_order_id侧 | sell_order_id侧 | 按映射取被动侧 |
|---|---:|---:|---:|
| A：任意snapshot/订单ID见证的collector接收钟严格早于成交报告 | 9 | 40 | 44 |
| B：snapshot/created/changed候选见证，local和source microtimestamp均严格早于trade | 4 | 39 | 43 |
| C：窗口任意匹配引用与trade同源microtimestamp | 50 | 50 | 50 |
| C：首次见证是changed/deleted | 0 | 7 | 7 |
| C：其中首次changed/deleted与trade同源microtimestamp | 0 | 6 | 6 |
| D：所有引用都在collector收到成交报告之后 | 41 | 10 | 6 |
| E：窗口内完全未找到该ID | 0 | 0 | 0 |
| 任一引用与trade完全同capture时间 | 0 | 0 | 0 |

这里“首次”按原响应最早行机械选择；A包含删除事件，所以不代表仍活跃挂单。B排除删除事件，但没有重建后续状态，仍不保证它在目标时刻未撤销/已进入有效队列。C的同源戳或changed/deleted不能自动判因果，可能涉及成交诱发更新；与A/B重叠并不矛盾。同capture为0只限本样本；规则未借行序制造正提前量。E为0仅表示整个窗口能找到，不代表成交前全覆盖。

本次没有一笔被动侧是由**成交报告前已收到的snapshot**贡献可见性；A的44笔均有更早订单事件见证。逐侧、逐笔布尔、首次引用行/类型及时间提前量见trade-coverage.csv；完整字段路径/原始7位时间见per-trade-field-witnesses.json。

## 2. 机械字段见证：报告前看见不等于撮合前可行动

以下均按该类别最早trade行取例，不挑最大提前量；时间均为2026-07-01 UTC，source字段是原生微秒整数，local原文保留7位并以整数100ns ticks比较。

- **B例：trade第261行，type0，被动sell ID `2023542863798273`。** 最早合格见证第67行order_changed：local `00:00:00.5658919Z`、source `1782864000525000`；trade local `00:00:01.0738365Z`、source `1782864001048000`。两钟均严格更早。该ID见证不说明未出现中途删除，也没有检验当时信息能否预测成交结果。
- **A而非B、同源戳例：trade第68行，被动ID同上。** 同一第67行changed的local严格早于trade `00:00:00.5712056Z`，但两者source均为`1782864000525000`。这是collector先收到更新、后收到成交报告的具体例子，不能把前后报告差当作交易所撮合前的机会；本次未独立证明该更新一定由此成交诱发。
- **D例：trade第262行，被动sell ID `2023542881275914`。** 成交local `00:00:01.0761930Z`；最早见证第273行order_deleted local `00:00:01.1112422Z`，源钟与trade同为`1782864001048000`。删除报告不能当作此前可见的活跃挂单状态。

**旧两条快照匹配的纠正边界：** trade第484/526行均为type0、被动sell侧。snapshot第665行local `00:00:02.7372039Z`，晚于两条trade各自的`00:00:02.4416924Z`及`00:00:02.5832150Z`；即使snapshot源钟早于trade，也不能以尚未收到的snapshot充当前视输入。不过本次另找到更早的created事件：

| trade行 / 被动ID | 已先收到的created行 | created local / source | trade source |

| 484 / 2023542896033793 | 433 | 00:00:02.0451515Z / 1782864002009000 | 1782864002417000 |
| 526 / 2023542896037888 | 435 | 00:00:02.0455159Z / 1782864002010000 | 1782864002562000 |

所以这两笔的B证据来自created，**不是**把迟到snapshot倒填回去。固定两笔的完整原字段见historical-two-snapshot-matches.json。

## 3. 能支持的“事前判断”层级与不能推出的结论

已支持：在供应商collector观察顺序内，有一部分订单ID及created/changed候选记录确实早于后来的成交报告；可明确区分先见、同源戳及只在报告后才见。B进一步限定到两套字段都严格更早，避免仅按报告先后包装先验。原件SHA匹配固定样本，结论不是合成示例。

未支持：用户本机也在同一时刻收到；source时间精确等于撮合引擎的可操作边界；订单当时仍有效、排队优先级和自身位置；该身份是否有预测不利成交的区分力；能在执行前发出并完成撤单。两钟误差界、本人接收/计算/路由与撤单生效延迟尚无证据。因此A是信息性下界，B是更强的字段/钟先后证据，**二者均不是交易所真实成交前可行动的充分条件**。本次没有读取价格变化、数量状态、费用或收益，不能声称事前识别赢家/坏单，不能把43/50解释为预测准确率或获利覆盖率。
