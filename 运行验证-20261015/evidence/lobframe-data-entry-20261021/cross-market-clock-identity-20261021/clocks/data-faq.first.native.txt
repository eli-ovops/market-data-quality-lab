L6: ## Data types and formats
L7: ### What data types do you support?
L8: 
L9: We provide historical market data [sourced from real-time WebSocket APIs](#why-data-source-matters-websocket-feeds-vs-rest-endpoints). Data is available in exchange-native format via the [raw data replay API](/api/http-api-reference.md#data-feeds-exchange), in normalized CSV datasets, and in normalized format via the [client libraries](/api/quickstart.md).
L10: The following normalized **tick-level** data types are available via [downloadable CSV data files](/downloadable-csv-files/overview.md):
L11: * [trades](/downloadable-csv-files/data-types.md#trades)
L12: * [incremental order book L2 updates](/downloadable-csv-files/data-types.md#incremental_book_l2)
L13: * order book snapshots ([top 25](/downloadable-csv-files/data-types.md#book_snapshot_25) and [top 5](/downloadable-csv-files/data-types.md#book_snapshot_5) levels)
L14: * [options\_chain](/downloadable-csv-files/data-types.md#options_chain)
L15: * [quotes](/downloadable-csv-files/data-types.md#quotes)
L16: * [book\_ticker](/downloadable-csv-files/data-types.md#book_ticker) (best bid/ask from native exchange BBO feeds)
L17: * [derivative tick info](/downloadable-csv-files/data-types.md#derivative_ticker) (open interest, funding rate, mark price, index price)
L18: * [liquidations](/downloadable-csv-files/data-types.md#liquidations)
L19: The [raw data replay API](/api/http-api-reference.md#data-feeds-exchange), available for [Professional and Business subscriptions](/faq/billing-and-subscriptions.md#what-are-the-differences-between-subscription-types), provides [exchange-native data](#what-is-a-difference-between-exchange-native-and-normalized-data-format). See [historical data details](/historical-data-details.md) for captured channels, symbols, and date ranges for each exchange.
L20: Captured channels correspond to exchange-specific data feeds, for example [Binance `bookTicker`](/historical-data-details/binance.md#captured-real-time-channels) or [BitMEX liquidation](/historical-data-details/bitmex.md#captured-real-time-channels) channels.
L21: The following [normalized data types](#what-is-a-difference-between-exchange-native-and-normalized-data-format) are also available via the [client libraries](/api/quickstart.md). Normalization runs client-side using raw data replay as the data source:
L22: * trades
L23: * order book L2 updates
L24: * order book snapshots (tick-by-tick, 10ms, 100ms, 1s, 10s etc)
L25: * quotes
L26: * book ticker (best bid/ask from native BBO feeds)
L27: * derivative tick info (open interest, funding rate, mark price, index price)
L28: * liquidations
L29: * options summary
L30: * OHLCV
L31: * volume/tick based trade bars
L32: ### What does high frequency historical data mean?
L33: For each exchange, we record the highest granularity available from its [real-time WebSocket feeds](#why-data-source-matters-websocket-feeds-vs-rest-endpoints). High frequency can mean different things because exchange APIs differ.
L34: For [Coinbase Exchange](/historical-data-details/coinbase.md), it can mean [L3 order book data](/faq/order-books.md#what-l3-order-book-data-can-be-used-for); for [Binance USDS-M Futures](/historical-data-details/binance-futures.md), all [L2](/faq/order-books.md#what-l2-order-book-data-can-be-used-for) order book updates; for [Binance Spot](/historical-data-details/binance.md), order book updates aggregated in 100ms intervals.
L35: ### What is a difference between exchange-native and normalized data format?
L36: 
L37: Cryptocurrency markets are very fragmented and every exchange provides data in its own bespoke format, which we call **exchange-native data format**.
L38: 
L39: Our [HTTP API](/api/http-api-reference.md#data-feeds-exchange) and [client libs](/api/quickstart.md) can provide market data in this format, meaning data you receive is exactly the same as the live data you would have received from exchanges ("as-is").
L40: {% hint style="info" %}
L41: See [how we collect data](/historical-data-details.md#market-data-collection-overview) in exchange-native format and [why it's important](#why-data-source-matters-websocket-feeds-vs-rest-endpoints).

L141: ### Do you provide market data in normalized format?
L142: 
L143: [Normalized market data](#what-is-a-difference-between-exchange-native-and-normalized-data-format) (unified data format for every exchange) is available via our [official libraries](/api/quickstart.md) and [downloadable CSV files](/downloadable-csv-files/overview.md). Our [HTTP API](/api/http-api-reference.md#data-feeds-exchange) provides data only in [exchange-native format](#what-is-a-difference-between-exchange-native-and-normalized-data-format).
L144: ### What is the difference between `book_ticker` and `quote`?
L145: 
L146: Both provide best bid/ask (BBO) data, but from different sources:
L147: * **`book_ticker`** — sourced from exchanges' native WebSocket BBO channels (e.g., Binance `bookTicker`, Bybit `orderbook.1`). Available via [client libraries](/api/quickstart.md), [tardis-machine](/tardis-machine/quickstart.md) and [CSV datasets](/downloadable-csv-files/data-types.md#book_ticker). See [which exchanges support it](#which-exchanges-support-book_ticker-data-type).
L148: * **`quote`** (alias for `book_snapshot_1_0ms`) — derived from L2 order book data. Available on all exchanges that provide L2 data. Also available as [`quotes` CSV dataset](/downloadable-csv-files/data-types.md#quotes).
L149: Update frequency differs between the two and depends on the exchange. For example, on Binance Spot the native `bookTicker` stream fires significantly more often than L2-derived quotes, because the exchange publishes a dedicated BBO update on every best-price change. On other exchanges the difference may be smaller or negligible. Check the update rates for your specific exchange before choosing.
L150: When using the [replay API](/api/quickstart.md), `book_ticker` can be replayed starting from any point in time since it is a standalone exchange feed. In contrast, `quote` is derived from L2 order book state, which requires an initial snapshot to reconstruct — snapshots are provided at 00:00 UTC each day (and after each [WebSocket reconnect](#how-frequently-do-exchanges-drop-websocket-connections)), so replay should start from 00:00 UTC to get accurate quotes.
L151: ### Does Tardis provide precomputed indicators or OHLCV candles?
L152: 
L153: Tardis provides raw tick-level market data (trades, order book updates, funding rates, liquidations, etc.) — not precomputed indicators, aggregated Kline/OHLCV candles, or hosted analytics. OHLCV bars and other derived metrics can be computed client-side from our data, for example using `trade_bar` data type in [tardis-machine](/tardis-machine/quickstart.md) or [client libraries](/api/quickstart.md).
L154: ### Do you provide time based aggregated data as well?
L155: 
L156: Our APIs (both [HTTP](/api/http-api-reference.md#data-feeds-exchange) and [CSV datasets](/downloadable-csv-files/api.md#datasets-api-details)) provide tick-level data only and do not support time-based aggregated data.
L157: If you need aggregated data (OHLC, interval-based order book snapshots), our [client libs](/api/quickstart.md) can compute it, but aggregation runs client-side from tick-level data, so it is slower than downloading pre-aggregated files.
L158: ### What is the `channel` field used in the HTTP API and client libs `replay` functions?
L159: When exchanges publish real-time data messages, they always publish them for the subscription topics clients subscribed to. These subscription topics are also often called "channels" or "streams" in exchange documentation and describe the data type a given message belongs to.
L160: For example, [Binance Spot](/historical-data-details/binance.md) publishes its trade data via [trade channel](/historical-data-details/binance.md#captured-real-time-channels) and order book L2 update data via [depth](/historical-data-details/binance.md#captured-real-time-channels).
L161: Since we collect the data for all the channels described in exchanges' details page ([Captured real-time market data channels section](/historical-data-details/binance.md#captured-real-time-channels)) our [HTTP API](/api/http-api-reference.md#data-feeds-exchange) and [client libs](/api/quickstart.md) offer filtering capability by those channels names, so for example to get historical trades for [Binance Spot](/historical-data-details/binance.md), channel [trade](/historical-data-details/binance.md#captured-real-time-channels) needs to be provided alongside requested instruments symbols (via HTTP API or client lib `replay` function args).
L162: ### How are CSV datasets split into files?
L163: CSV datasets are available in daily intervals split by exchange, data type, and symbol. In addition to standard currency pairs/instrument symbols, each exchange also has special [grouped symbols](/downloadable-csv-files/overview.md#grouped-symbols) available depending on whether it supports a given market type: SPOT, FUTURES, OPTIONS, PERPETUALS, COMBOS, and PREDICTIONS.
L164: That feature is useful if someone is interested in, for example, all Deribit's options instruments trades or quotes data without requesting data for each symbol separately.
L165: ## Data sources and collection
L166: ### How is historical raw market data sourced?
L167: 
L168: Raw market data is sourced from exchanges' real-time WebSocket APIs. For cases where an exchange lacks a WebSocket API for a particular data type, we fall back to polling a REST API periodically, e.g., Binance USDS-M Futures open interest data.
L169: {% hint style="info" %}
L170: See [market data collection overview](/historical-data-details.md#market-data-collection-overview) for more details and why [data source matters](#why-data-source-matters-websocket-feeds-vs-rest-endpoints).
L171: {% endhint %}
L172: ### Why data source matters — WebSocket feeds vs REST endpoints
L173: 
L174: Recording exchanges' real-time WebSocket feeds preserves [the most granular data](#what-does-high-frequency-historical-data-mean) that exchanges publish, including tick-level order book updates that are not available via REST APIs.
L175: WebSocket-sourced historical data reflects what a live trading client would have received, including exchange-side behavior such as [connection drops](#is-provided-raw-market-data-complete), publishing delays during volatile periods, [duplicated trades](#do-exchanges-publish-duplicate-trades), or [crossed books](/faq/order-books.md#can-reconstructed-order-books-have-bid-ask-overlap) in edge cases.
L176: This makes it useful for market microstructure research and realistic replay, but it also means raw data is not corrected after the fact.
L177: For example, during volatility an exchange may publish WebSocket messages with higher-than-usual latency or batch delayed updates. A REST endpoint may return a cleaner history after the fact, but it will not show the conditions a live client saw at that time.
L178: 
L179: {% hint style="info" %}
L180: See [market data collection overview](/historical-data-details.md#market-data-collection-overview) for more details.
L181: {% endhint %}
L182: ### What is the historical market data delay in relation to real-time?
L183: 
L184: For [raw data replay API](/api/quickstart.md) the most recent data available is approximately T-6 minutes from the current time.
L185: 
L186: [Downloadable CSV files](/downloadable-csv-files/overview.md) for a given day are available on the next day around 06:00 UTC — see [CSV readiness](/downloadable-csv-files/overview.md) for details.
L187: ### Can you record market data for an exchange that's not currently supported?
L188: 
L189: Yes, we're always open to support new promising exchanges. [Contact us](https://tardis.dev/#contact) and we'll get back to you to discuss the details.

L191: ## Instruments and symbols
L192: ### How do symbol IDs differ between raw replay and CSV datasets?
L193: 
L194: The [`/exchanges/:exchange`](/api/http-api-reference.md#exchanges-exchange) API returns two separate symbol lists with different ID formats:
L195: * **`availableSymbols[].id`** — used for [raw data replay](/api/http-api-reference.md#data-feeds-exchange). These are exchange-native symbol IDs as used in WebSocket subscriptions (e.g., `btcusdt` for Binance, `BTC-PERPETUAL` for Deribit).
L196: * **`datasets.symbols[].id`** — used for [CSV dataset downloads](/downloadable-csv-files/overview.md). These are CSV dataset symbols: they are uppercased, and `/` and `:` are replaced with `-`. They can still contain non-ASCII or reserved URL characters, so URL-encode the symbol path segment when constructing dataset URLs manually. Official clients do this automatically.
L197: The [Instruments Metadata API](/api/instruments-metadata-api.md) provides `id` for exchange-native symbols and `datasetId` for CSV dataset symbols after the symbol appears in exported dataset metadata.
L198: ### Does your historical data include delisted or expired instruments?
L199: 
L200: Yes. Our historical datasets are free of survivorship bias — they include all instruments that were actively trading at the time of data collection, including those that have since been delisted, expired, or renamed by the exchange.
L201: Note that for some spot exchanges, early historical coverage was limited to high-cap currency pairs only. See individual exchange pages in [Historical Data Details](/historical-data-details.md) for exact coverage boundaries and start dates.
L202: ### Can the same symbol ID refer to different assets over time?
L203: 
L204: Yes. Exchanges may reuse symbol identifiers for different assets — for example, delisting a token and later listing a different token under the same symbol. Tardis passes through symbol IDs as provided by the exchange without modification, so the same symbol string may appear across different time periods for different underlying assets. Verify token identity using additional context such as price levels or exchange announcements.
L205: ### Do you provide historical futures data?
L206: 
L207: Yes. We provide historical futures and perpetual swaps data across leading derivatives venues. See [Historical Data Details](/historical-data-details.md) for the current exchange list and per-exchange coverage.
L208: ### What is the difference between futures and perpetual swaps contracts?
L209: 
L210: Futures contract is a contract that has expiry date (for example quarter ahead for quarterly futures). Futures contract price converges to spot price as the contract approaches expiration/settlement date. After futures contract expires, exchange settles it and replaces with a new contract for the next period (next quarter for our previous example).
L211: A perpetual swap contract, also commonly called "perp", "swap", "perpetual", or "perpetual future" in crypto exchange nomenclature, is very similar to a futures contract but does not have an expiry date (hence perpetual). To ensure that the perpetual swap contract price stays near the spot price, exchanges employ a mechanism called funding rate. When the funding rate is positive, Longs pay Shorts. When the funding rate is negative, Shorts pay Longs.
L212: This mechanism can be quite nuanced and vary between exchanges, so it's best to study each contract specification to learn all the details (funding periods, mark price mechanisms, etc.).
L213: {% hint style="info" %}
L214: See CSV [grouped symbols section](/downloadable-csv-files/overview.md#grouped-symbols) if you'd like to download data for all futures or perpetual swaps as a single file for given exchange instead one by one for each individual instrument.
L215: {% endhint %}
L216: ### Do you provide historical options data?
L217: Yes, we do provide historical options data for [Binance European Options](/historical-data-details/binance-european-options.md), [OKX Options](/historical-data-details/okex-options.md), [Deribit](/historical-data-details/deribit.md), [Bybit Options](/historical-data-details/bybit-options.md), [Kraken Futures](/historical-data-details/cryptofacilities.md), [Bullish](/historical-data-details/bullish.md), and [HTX Options](/historical-data-details/huobi-dm-options.md) (delisted) - see [options chain](/downloadable-csv-files/data-types.md#options_chain) CSV data type and the corresponding exchange details pages.
L218: ### Do you provide normalized contract amounts for derivatives?
L219: 
L220: Data we provide has contract amounts exactly as provided by exchanges' APIs, meaning the `amount` field may represent contracts, base-asset units, or USD depending on the exchange. This can be tricky when comparing across exchanges due to different contract multipliers (e.g., OKX where each contract has a $100 value) or different contract types (linear or inverse).
L221: We provide the [instruments metadata API](/api/instruments-metadata-api.md) that returns `contractMultiplier`, `inverse`, `contractType`, tick sizes, and more for each instrument in a uniform way, allowing you to normalize contract amounts client-side. Use the following formulas for **futures and perpetual contracts**:
L222: | Contract type             | Base-asset volume                     | USD notional                          |
L223: | ------------------------- | ------------------------------------- | ------------------------------------- |
L224: | Linear (`inverse: false`) | `amount × contractMultiplier`         | `amount × contractMultiplier × price` |
L225: | Inverse (`inverse: true`) | `amount × contractMultiplier / price` | `amount × contractMultiplier`         |
L226: {% hint style="warning" %}
L227: These formulas apply to standard futures and perpetual contracts. Quanto contracts (`quanto_future`, `quanto_perpetual`) and options require different treatment — consult exchange-specific documentation for their volume calculations.
L228: {% endhint %}
